# Eye-tracking Experiment Platform for Gazepoint GP3

Проект для проведения экспериментов по когнитивной нагрузке с использованием айтрекера **Gazepoint GP3**, интерактивных веб-страниц и собственной инфраструктуры записи/анализа.

Режим эксперимента: **pd** (Progressive Disclosure) — исследование прогрессивного раскрытия информации в дизайне 2×3 (flat vs. sections × lookup/comparison/diagnosis).

Функции:

- запуск стимулов через встроенный браузер (pywebview);
- управление логикой эксперимента (тайминги, idle-курсора, последовательность задач);
- запись данных взгляда с GP3 через OpenGaze API (PyOpenGaze);
- запись событий эксперимента (start/end/markers/questionnaires);
- запись экрана (ffmpeg + mss);
- пост-hoc генерация видео с оверлеем взгляда и курсора (отдельным скриптом);
- анализ метрик когнитивной нагрузки (фиксации, зрачок, сканпуть);
- сборка в автономный `.exe` (PyInstaller).


## 1. Архитектура

### 1.1. Компоненты

- **Gazepoint Control** — официальное приложение от Gazepoint:
    - подключается к GP3;
    - управляет калибровкой;
    - открывает **OpenGaze API** по TCP (по умолчанию `localhost:4242`).

- **PyOpenGaze** (`PyOpenGaze/opengaze.py`) — Python-клиент для OpenGaze API:
    - TCP-соединение с Gazepoint Control;
    - включение потоков данных (взгляд, курсор, зрачок, фиксации);
    - запись лога в TSV (TIME, FPOGX, FPOGY, FPOGD, LPD, RPD и др.);
    - отправка маркеров в колонку USER (TRIAL_START, PD_TASK_START и т.п.).

- **Flask-сервер** (`server.py`):
    - раздаёт HTML-страницы стимулов (инструкции, формы, PD-консоль, опросники);
    - принимает события от JavaScript через POST `/event`;
    - хранит thread-safe очередь событий для чтения оркестратором.

- **Встроенный браузер / pywebview** (`pywebview`):
    - создаёт полноэкранное окно с Chromium-движком;
    - открывает страницы Flask-сервера;
    - оркестратор навигирует через `window.load_url()`.

- **Фронтенд стимулов**:
    - `static/experiment.js` — базовый модуль: `sendEvent()`, `PAGE_LOADED`, idle-детектор (все страницы);
    - `static/pd_console.js` — PD-специфичная логика: sidebar, рендер ресурсов, секции, AOI-снэпшоты, счётчик кликов.

- **Оркестратор эксперимента** (`experiment.py`, класс `Experiment`):
    - запускает pywebview-окно и Flask в фоне;
    - подключается к GP3 или запускает mock-режим;
    - управляет последовательностью страниц и ожидает события из очереди;
    - запускает/останавливает запись экрана и GP3;
    - логирует события в CSV.

- **Запись экрана** (`screen_recorder.py`):
    - захват кадров через **mss**, кодирование через **ffmpeg** (imageio-ffmpeg или системный);
    - стабильный FPS по таймеру, корректные метаданные видео для синхронизации с GP3.

- **Скрипт оверлея** (`overlay.py`):
    - читает видео экрана и TSV-лог GP3;
    - синхронизирует таймлайны;
    - рисует поверх видео траекторию взгляда (красный круг) и курсор (зелёная точка).

- **Генерация оверлеев** (`generate_overlays.py`):
    - запускается вручную после сессии: `python generate_overlays.py <participant_id> [data_dir]`;
    - находит gaze-файл и видеозаписи участника, определяет маркеры блоков из events CSV;
    - генерирует до 3 оверлеев: PD-блок 1, PD-блок 2, фаза картин;
    - реализация рендеринга — в `overlay.py`, этот скрипт только оркестрирует вызовы.

- **Скрипты анализа** (папка `analysis/`):
    - `pupil_preprocessing.py` — **модуль очистки зрачкового сигнала** по Mathôt & Vilotijević (2023): бинокулярное усреднение, speed filter, margin, интерполяция, outlier pass, три варианта baseline-коррекции (субтрактивная/z/процентная);
    - `inspect_pupil_speed.py` — CLI-калибровка порога speed filter: строит гистограмму |ΔD| по всем TSV, сохраняет PNG;
    - `analysis_paintings.py` — тепловые карты, траектории, XLSX для фазы картин;
    - `analysis_pd.py` — per-participant ET-метрики PD-блоков: вызывает `pupil_preprocessing`, считает фиксации/саккады/зрачок/AOI, сохраняет XLSX;
    - `pd_analysis.py` / `pd_analysis.ipynb` — **групповой анализ PD** (все участники): ET-метрики по условию и заданию, подсчёт баллов SAN/STAI/NASA-TLX, корреляции Спирмена, графики зрачка во времени;
    - `group_analysis_pd.py` — групповой статистический анализ PD-эксперимента (Wilcoxon flat vs sections, FDR);
    - `group_analysis.py` — устаревший групповой анализ (aws/gcp), оставлен для справки.

## 3. Настройка Gazepoint Control (Windows)

1. Установить Gazepoint Control с официального сайта.
2. Подключить GP3 к USB 3.0.
3. Запустить Gazepoint Control:
    - выполнить калибровку (9 точек);
    - проверить, что в Live View видно движения взгляда.
4. Убедиться, что **OpenGaze API включён**:
    - во вкладке **Settings → API TCP/IP Settings** проверить **Control Port** (обычно `4242`) и **Control Address** (например `127.0.0.1`).
    - в `config.py` значения `GP3_HOST` и `GP3_PORT` должны **точно совпадать** с Control Address и Control Port из Gazepoint Settings.

Gazepoint Control должен оставаться запущенным на протяжении всего эксперимента.

## 4. Конфигурация проекта: `config.py`

### 4.1. Основные параметры

```python
# ===== Режим эксперимента =====
EXPERIMENT_MODE = 'pd'         # единственный режим

CURSOR_IDLE_THRESHOLD = 10000  # мс (JavaScript)

# ===== Gazepoint =====
GP3_HOST = '127.0.0.1'         # из Gazepoint Settings → Control Address
GP3_PORT = 4242                # из Gazepoint Settings → Control Port

# ===== Flask =====
FLASK_HOST = '127.0.0.1'
FLASK_PORT = 5000

# ===== Видео =====
RECORD_SCREEN = True
VIDEO_FPS = 30
VIDEO_MONITOR = 1              # индекс монитора (1 = primary)
OVERLAY_DRAW_INVALID_GAZE = True  # рисовать невалидный взгляд (жёлтым)

# ===== Калибровка =====
MAX_CALIBRATION_ERROR = 40.0   # допустимая средняя ошибка GP3

# ===== Данные =====
DATA_DIR = 'data'

# ===== Режимы отладки =====
EYE_TRACKER_MOCK = False       # True = не подключаться к GP3
CURSOR_ONLY_MODE = False       # True = писать только курсор мыши (для проверки оверлея)
```

> ⚠️ **Перед реальным запуском** убедитесь, что `EYE_TRACKER_MOCK = False` и `PD_SKIP_BLOCKS = False`.

### 4.2. Параметры фазы картин

```python
PAINTINGS_DIR = 'paintings'
PAINTING_DISPLAY_TIME = 15.0       # с показа каждой картины
PAINTING_FEEDBACK_TIME = 2.0       # с фиксационного крестика после картины
PAINTING_CORNER_CALIBRATION = True # corner-калибровка перед фазой
CALIB_PAINTING_FILE = 'calib_painting.jpg'
CALIB_PAINTING_DISPLAY_TIME = 15.0
BASELINE_DURATION = 2.0            # с фиксационного ITI
```

### 4.3. Параметры PD-эксперимента

```python
# Две независимые оси counterbalancing:
PD_GROUP = 1              # 1 или 2 — порядок УСЛОВИЙ (flat/sections)
PD_DATASET_ORDER = 1      # 1 или 2 — порядок ДАТАСЕТОВ (alpha/beta), независимо от PD_GROUP
PD_TASK_ORDER_INDEX = 0   # какой из 4 valid_orders из tasks.json использовать (0-3)
PD_ITI_DURATION = 2.0     # с baseline между задачами
PD_SKIP_BLOCKS = False    # True = пропустить PD-блоки, перейти сразу к картинам (отладка)
```

Дизайн 2×2:

| PD_GROUP | PD_DATASET_ORDER | Блок 1 | Блок 2 |
|---|---|---|---|
| 1 | 1 | flat+alpha | sections+beta |
| 1 | 2 | flat+beta | sections+alpha |
| 2 | 1 | sections+alpha | flat+beta |
| 2 | 2 | sections+beta | flat+alpha |

`PD_GROUP`, `PD_DATASET_ORDER` и `PD_TASK_ORDER_INDEX` можно задать в `flags.txt` без пересборки — принимают целое число:
```
PD_GROUP=2
PD_DATASET_ORDER=1
PD_TASK_ORDER_INDEX=1
```

## 10. PD-интерфейс: `static/pd_console.js`

### 10.1. Глобальное состояние

```javascript
let currentResourceType = null;      // 'vms' | 'dbs' | 'firewall' | 'loadbalancers' | 'networks'
let currentResourceId = null;        // e.g. 'api-prod-1'
let taskStartTime = null;            // performance.now() при загрузке
let clickCounter = 0;                // кликов в #main-layout
let openSections = new Set(['General']); // для conditions-режима
```

### 10.2. Инициализация

При `DOMContentLoaded`:
1. Записать `taskStartTime`.
2. Обнулить `clickCounter`.
3. Отправить `PD_TASK_START`.
4. Отрендерить список ресурсов первого типа из задачи.
5. Привязать счётчик кликов к `#main-layout`.

### 10.3. Рендер списка ресурсов (`renderResourceList`)

- Сбрасывает `currentResourceId`, `openSections`.
- Рисует breadcrumb: `CloudPanel > {TypeLabel}`.
- Генерирует таблицу (Name / Status / Key Info / Region).
- `data-aoi="resource-list"` для AOI-трекинга.
- Вызывает `reportAoiSnapshot()`.

### 10.4. Рендер детали ресурса (`renderResourceDetail`)

- Показывает заголовок с иконкой, ID, статус-бейдж.
- Рендерит секции в зависимости от `CONDITION`:
  - **flat**: все секции видимы, заголовки — текстовые разделители (неинтерактивные).
  - **sections**: заголовки — кнопки с шевроном (▾/▸); `General` раскрыта по умолчанию, остальные свёрнуты; несколько секций можно открыть одновременно.
- При переходе на другой ресурс `openSections` сбрасывается к `['General']`.
- Дебаунс 200 мс для `reportAoiSnapshot()` на скролл.

### 10.5. Контент секции (`renderSectionContent`)

- Отображает пары ключ–значение в grid-макете (210px | 1fr).
- Ключи, начинающиеся с `__table_NAME__`, рендерятся как `<table>` через `renderEmbeddedTable()`.
- Ячейки со значением "Unhealthy" подсвечиваются красным.

### 10.6. AOI-система (`reportAoiSnapshot`)

Все элементы с атрибутом `data-aoi` отслеживаются:

| `data-aoi` | Элемент |
|---|---|
| `task-bar` | Верхняя панель задачи |
| `sidebar` | Левая навигация |
| `breadcrumb` | Путь навигации |
| `resource-list` | Таблица ресурсов |
| `section-header-{name}` | Заголовок секции |
| `section-content-{name}` | Содержимое секции |

`reportAoiSnapshot()` использует `getBoundingClientRect()` для всех `[data-aoi]` элементов и отправляет `PD_AOI_SNAPSHOT` с координатами на экране. Вызывается: после каждого рендера + с дебаунсом 200 мс при скролле + после переключения секции.

### 10.7. Все JS-события PD

`PD_TASK_DONE` потребляется `_wait_for_event()` и пишется в events CSV как `PD_TASK_END_…`.
Все остальные события `pd_console` сбрасываются после каждого задания через `drain_page_events('pd_console')`
в файл `pd_<id>_b{N}_interactions.jsonl` (по одному JSON-объекту на строку).

| Событие | Ключевые поля | Сохранение |
|---|---|---|
| `PD_TASK_START` | `task_id`, `task_index`, `task_type`, `condition`, `dataset`, `block_num` | interactions.jsonl |
| `PD_SIDEBAR_CLICK` | `resource_type`, `task_id` | interactions.jsonl |
| `PD_RESOURCE_OPEN` | `resource_id`, `task_id` | interactions.jsonl |
| `PD_SECTION_TOGGLE` | `resource_id`, `section_name`, `new_state` ('open'/'closed'), `task_id` | interactions.jsonl |
| `PD_BREADCRUMB_CLICK` | `target`, `task_id` | interactions.jsonl |
| `PD_TASK_DONE` | `task_id`, `completion_time_ms`, `click_count`, `condition`, `dataset`, `block_num` | events CSV (PD_TASK_END_…) |
| `PD_AOI_SNAPSHOT` | `task_id`, `aois[]` (name/x/y/w/h/visible), `screen_w`, `screen_h` | interactions.jsonl |
| `PD_NASA_TLX_RATINGS_DONE` | `block_num`, `scores:{mental,temporal,performance,effort,frustration}` | events CSV |
| `PD_NASA_TLX_DONE` | `block_num`, `scores:{...5 шкал...}`, `weights:{...5 шкал, сумма=10...}`, `pairs:{mental_vs_temporal:'mental',...}` | NASA-TLX JSON |

Колонки: `relative_time`, `TIME`, `painting_x`, `painting_y`, `in_painting`, `BPOGX`, `BPOGY`, `BPOGV`, `FPOGX`, `FPOGY`, `FPOGD`, `FPOGID`, `FPOGV`, `LPD`, `RPD`, `LPV`, `RPV`, `LPUPILD`, `RPUPILD`, `USER`.

Координаты пересчитаны: нормализованные BPOG (0–1 от экрана) → пиксели экрана → пиксели картины (с учётом bounding box). Если взгляд за пределами картины — `painting_x`/`painting_y` = NaN.

**Важно — коррекция object-fit: contain** (исправлено 2026-03-30): `getBoundingClientRect()` возвращает CSS-бокс элемента (весь экран 1920×1080), а не реальную область отрисовки картины. `screen_to_image_coords()` теперь вычисляет настоящий content-rect через aspect-ratio fitting по натуральным размерам изображения. Для калибровочной картины используется `object-fit: fill` (растяжение без сохранения пропорций) — bbox содержит `fit_mode='fill'`, коррекция letterboxing не применяется.

## 14. Групповой анализ: `group_analysis_pd.py`

Групповой статистический анализ PD-эксперимента. Загружает `pd_*_metrics.xlsx` всех участников, агрегирует до уровня участника и проводит парные тесты.

### Дизайн тестирования

| Уровень | Метод | Единица | Семейство FDR |
|---|---|---|---|
| Главный эффект условия | Paired Wilcoxon flat vs sections | Среднее по 6 задачам участника | BH по всем метрикам |
| Условие × тип задачи | Paired Wilcoxon отдельно для lookup / comparison / diagnosis | Среднее по 2 задачам участника | BH внутри набора |

`tlx_weighted_score`, `tlx_unweighted_mean`, `score_mental/temporal/performance/effort/frustration`

### Входные данные

Графики трасс зрачка (§8.2–8.3) переведены на очищенный сигнал (`use_cleaned=True`). Primary метрика H1: `pupil_subtractive_avg` (вместо `pupil_pct_change_avg`).

### Входные данные

| Файл | Содержимое |
|------|-----------|
| `data/<pid>/gaze_<pid>_pd_b{1,2}_trial.tsv` | Гейз-данные блоков (все участники 4-значный ID) |

| `data/experiment conditions and nasa tlx.csv` | NASA-TLX баллы и веса + условия контрбалансирования |

### Что считается

**Айтрекинговые метрики (из `analysis_pd.analyze_participant`):**
- Средние длительность фиксации, число фиксаций, длина сканпути, диаметр зрачка
- Зрачок: три варианта baseline-коррекции (`pupil_subtractive_avg` primary, `pupil_z_avg` sensitivity, `pupil_pct_change_avg` legacy); QC-поля `task_pct_unrecoverable`, `task_n_valid`
- Агрегация по **условию** (flat / sections) и по **заданию** (A1–A6, B1–B6)

**NASA-TLX:**
- Невзвешенный = среднее 5 шкал (mental, temporal, performance, effort, frustration)
- Взвешенный = Σ(score_i × weight_i) / 15
- Сравнение flat vs sections

**SAN (Самочувствие-Активность-Настроение):**
- 30 пунктов, шкала 1–7; обратные пункты {3,4,9,10,13,15,16,21,22,27,28} → 8 − балл
- Субшкалы (среднее по 10 пунктам): С — самочувствие, А — активность, Н — настроение
- SAN1 (до) и SAN2 (после эксперимента), дельта

**STAI (ситуативная тревожность):**
- 20 пунктов; позитивные {1,2,5,8,10,11,15,16,19,20} → 5 − балл
- Суммарный балл 20–80; интерпретация: < 31 очень низкая, 31–45 умеренная, > 45 высокая

**Корреляции Спирмена (NASA-TLX × айтрекинг):**
- Уровень: участник × блок (N ≤ 18)
- ET-метрики: число фиксаций, длит. фиксации, длина сканпути, диаметр зрачка
- NASA-шкалы: TLX взвеш./невзвеш., mental, effort, frustration, temporal, performance
- Тепловая карта r с отметкой значимости (* p<0.05, ** p<0.01)
- Отдельные таблицы r для условий flat и sections

**Графики зрачка во времени:**
- Per-participant: фигура 3×4 (12 заданий), скользящее среднее ~15 сэмплов; синий=flat, оранжевый=sections
- Сводный: средний нормализованный ряд зрачка по заданию (ось X = доля времени задания)

## 20. Архитектурные заметки

### Флаги-ловушки в config.py и flags.txt

> ⚠️ **ВАЖНО:** `config.py` **компилируется в байткод** при сборке exe. Значения флагов
> фиксируются в момент `pyinstaller`. Файл `config.py` рядом с готовым exe **не читается**
> и ни на что не влияет — менять его после сборки бесполезно.

Для изменения флагов без пересборки создай файл **`flags.txt`** рядом с exe:

```
# flags.txt (можно редактировать без пересборки)
EYE_TRACKER_MOCK=false
CURSOR_ONLY_MODE=false
PD_SKIP_BLOCKS=false
PD_GROUP=2
PD_DATASET_ORDER=1
PD_TASK_ORDER_INDEX=1
```

- Строки с `#` — комментарии, игнорируются.
- Булевые флаги: `true`/`false`, `yes`/`no`, `1`/`0`.
- Целочисленные флаги (`PD_GROUP`, `PD_TASK_ORDER_INDEX`): голое число.
- Если файл отсутствует — используются значения по умолчанию из `config.py`.

Пример для тестового запуска только фазы картин без трекера:
```
EYE_TRACKER_MOCK=true
PD_SKIP_BLOCKS=true
```

### Генерация оверлеев

Оверлеи больше не генерируются автоматически в конце эксперимента — это позволяет сразу запускать следующего участника. Запускай вручную после переноса данных:
```bash
python generate_overlays.py <participant_id> data/
```
Генерирует до 3 оверлеев: PD-блок 1, PD-блок 2, фаза картин. Использует маркеры из events CSV и gaze TSV.

### PD-анализ метрик

`post_process_pd()` сохранён в коде (для справки), но не вызывается автоматически.
Для извлечения метрик:
```bash
python analysis_pd.py <participant_id> data/
```
Создаёт `pd_<id>_metrics.xlsx` с листами `per_task`, `per_block`, `summary`.

### cursor_recorder.py

Используется при `CURSOR_ONLY_MODE = True` (через `vibe_flags.txt` или config.py). Записывает TSV с колонками `TIME, CX, CY, USER` (без GP3). Удобно для проверки синхронизации оверлея.

> ⚠️ Если в gaze-TSV отсутствуют колонки `FPOGX`, `FPOGY` и др. (присутствуют только `TIME/CX/CY/USER`) — значит, был активирован `CURSOR_ONLY_MODE`. Данные взгляда в этом файле **отсутствуют**.
